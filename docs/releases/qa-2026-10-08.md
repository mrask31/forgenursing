## Release blocker: client-writable entitlements

Live read-only database inspection established:

- RLS is enabled on `public.profiles`.
- The `authenticated` role has table UPDATE permission, including `subscription_status`, `trial_ends_at`, `is_beta`, `beta_expires_at`, and Stripe ID columns.
- Owner policies allow updates when `auth.uid() = id`. The permissive ALL policy also applies to owners.
- Existing profile triggers initialize trials on INSERT and queue welcome email; none restricts changes to entitlement fields on UPDATE.
- `src/lib/subscription-access.ts` grants access for `subscription_status = 'active'`, an unexpired trial, or an active beta period. Middleware and protected API access use these profile values.

**Impact:** Ownership isolation does not protect privileged fields within a user's own row. A signed-in user can potentially self-grant subscription/trial/beta access through direct data updates. This is an authorization defect, not evidence that anyone has exploited it. No exploit or entitlement modification was performed.

**Required correction:** Remove client authority to insert/update/delete privileged profile data; allow only documented self-service preference fields. Keep entitlement writes restricted to trusted provisioning/admin/payment paths. Audit every profile mutation before applying restrictions so settings, trial provisioning, and Stripe reconciliation continue working. Regression verification must demonstrate rejected direct entitlement changes, permitted ordinary settings changes, successful signup provisioning, and successful trusted Stripe updates using QA data.
